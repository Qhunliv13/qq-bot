# 架构与消息流

本文说明插件内部的**数据流、决策流程与模块职责**。所有内容与具体部署无关。

---

## 一、整体位置

```
QQ 客户端
   │
   ▼
OneBot 实现（NapCat / Lagrange …）
   │  ① 反向 WebSocket：把群消息事件推给 AstrBot
   │  ② HTTP 接口：插件用它查群列表 / 成员名单 / 登录状态
   ▼
AstrBot（宿主）
   │  · 平台适配器：收事件、提供 Provider（LLM）、发送消息
   │  · 插件 astrbot_plugin_group_ai
   ▼
OpenAI 兼容的对话接口（Provider）
```

插件**不直接连 QQ**，只与 AstrBot 交互；唯一"绕过" AstrBot 的地方是**通过 OneBot 的 HTTP
接口读群成员名单**（用于感知加群/退群），这是**只读**用途。

---

## 二、模块职责

| 模块 | 职责 | 说明 |
|---|---|---|
| `main.py` | 事件接入、回复决策、各能力编排 | 插件主体，唯一注册进 AstrBot 的模块 |
| `config.py` | **实例配置**：管理员、自称、人设、群范围、OneBot 地址 | 实例间会不同的值都在这里 |
| `prompts.py` | 提示词模板 + 通用默认人设 | 文案与逻辑分离；调用方按配置拼装 |
| `_conf_schema.json` | 配置面板 schema | AstrBot 据此生成 WebUI 配置项与落盘文件 |

`main.py` 顶部的常量是**项目级调参**（频率、超时、图片边长…），对所有使用者都成立。

---

## 三、一条消息的完整流程

```
① 收到群消息（AstrBot 事件）
   │  · 记录到该群的短期上下文（供后续判断使用）
   │  · 若带图 → 落盘位置记录下来（"最近图"缓存）
   │  · 收集图到表情包库（异步打标签）
   ▼
② 频率与范围检查
   │  · 群是否在 target_groups 内？不在直接返回
   │  · 距上次回复是否太近？被 @ 时用更宽的间隔
   ▼
③ 判断"要不要回"
   │  · 被 @ / 被引用 → 必回（走"直接回复"提示词）
   │  · 否则 → 让模型决定（走"自主判断"提示词）
   │     插件先把判断线索拼进提示词：发言人身份、@ 了谁、
   │     是否引用了别人的话、最近是否恰有两人一问一答
   ▼
④ 生成回复（一次 LLM 调用）
   │  · 人设在最前 + 能力清单（可用的标记）+ 表情包关键词目录
   │  · 按需附带图片（本条消息的图 / 被引用的图 / 被问到的头像 / 最近那张图）
   │  · 注入当前时间与"机器人自己的头像描述"
   │  · 超时则本次不回（不阻塞后续消息）
   ▼
⑤ 解析回复里的标记（工具调用）
   │  · [搜索:…]  → 搜索 + 打开网页读正文 → 把材料回灌模型再生成一次
   │  · [下图:…]  → 搜图/下载
   │  · [头像:QQ] → 取该成员头像
   │  · [表情包:…] → 模糊搜索候选 → 让模型看图挑一张
   │  · [删表情:…] → 从索引移除
   ▼
⑥ 发送（引用被回复的那条消息 + 文字 + 按需附图）
```

**并发控制**：同一群同时只处理一条消息；新消息到达时只保留**最新一条**待处理
（避免连发时回复错位）。

## 四、几个关键设计

### 4.1 为什么用"标记"而不是完整 ToolSet

插件的每个能力（搜索、看图、发表情包）都需要**多轮交互**（先决定、再取数据、再生成）。
用方括号标记把这条链路写在插件里，比把工具 schema 交给模型、再处理工具调用回调
少一层接线，模型也更容易稳定输出。代价是解析要宽容：兼容各种括号与全角冒号，
并对未识别的标记做兜底清洗（绝不把标记当文字发出去）。

### 4.2 为什么挑表情包要让模型"看图"

只给关键词描述时，模型是在**盲选**标签，容易挑到不搭的图。改成把候选图**直接交给模型**
（连同标签），它就能"看得见再挑"，一次调用同时完成"挑图"和"判断合不合适"。

### 4.3 为什么动图要抽多帧

只取首帧时，模型看不到"先怎样、后怎样"的过程，容易理解错。抽若干帧横向拼成一张长条图，
既保留过程信息，又只占**一张图**的 token 开销。

### 4.4 为什么图片要先压缩

视觉接口的耗时与请求体积强相关。原图 base64 后可能达到数 MB，单次调用可达上百秒；
而"这张图合不合适"这类判断用几百像素的缩略图就够了。压缩后通常能降一个数量级。
压缩结果应做缓存（同一张图不必反复压）。

### 4.5 为什么"被 @ "要有独立的频率限制

非 @ 回复需要限流以免刷屏；但对方**明确呼叫**时若也套用大间隔，就会出现"叫了不理"。
因此两者分开：非 @ 用较严的间隔与每分钟上限，被 @ 用宽松得多的一组。

### 4.6 记忆与状态的边界

插件在内存里维护三类**每群**状态：

| 状态 | 用途 | 生命周期 |
|---|---|---|
| 短期上下文（最近若干条） | 供判断"是否在对话中"、给模型提供语境 | 进程内，随重启清空 |
| 最近图片引用 | 支持"看看刚才那张图" | 进程内，滚动覆盖 |
| 成员名单快照 | diff 出加群/退群 | 进程内，首次只建基线 |

需要跨重启保留的只有**表情包索引**（落盘在 `data/stickers/manifest.json`）与
**机器人头像描述缓存**。
