# 屏幕点击视觉检查点（2026-10-28）

## 现有问题与增量修正

线上旧版 VM 的预览与直接点击路由彼此独立；`click_confirm` 只用进程全局坐标和 120 秒时间，甚至允许请求覆盖 x/y，且不校验画面或实际鼠标命令返回码。独立的 `vm_click_text` 原先也可直接点击。它们不能证明模型看过标点，不能防止过期画面点错。原始 VM API 属于生产主机文件，保持原样，不能以插件变更冒充整个服务的安全升级。

插件增加唯一 `vm_click_gate.ClickGate`（每个原生模型回合一实例）：

1. `vm_click_preview(x,y,label)` 读取实际 PNG 截图像素，校验文件为预期截图目录中的普通文件、图片大小与坐标；在新的私有随机文件内画十字点并将其作为独立图像观察送进模型，返回随机一次性 ticket、坐标、宽高和未标点像素 SHA-256。仅返回路径或文字不算模型已看图。
2. 下一次含标点图像的模型请求成功返回后，才把对应 ticket 标记为模型已收到；图像转换失败或没有纳入视觉请求不能标记。`vm_click_confirm(ticket,x,y,screen_sha256,viewed=true)` 必须在同一模型回合再次调用，ticket、坐标、hash 和布尔确认一致，并在 60 秒有效期内。
3. 确认时再截屏，比较完整解码 RGB 像素和尺寸，只有原样才调用原 VM 鼠标动作一次；任何错误或不确定回执都消耗 ticket，不重试，以免重复点击。旧直接 `vm_click`、`vm_click_text` 和旧 VM 预览/确认入口从插件工具通道拒绝，不把未经视觉核查的坐标落到底层。
4. `vm_type(text)` 依然一次传入整段文字，不要求模型逐字符调用。既有记忆、任务、授权、发送回执边界保持原样。

## 2026-10-30 插件传输边界增量

检查实际模型 schema → `_dispatch_tool` → `_vm_tool` 后发现，`vm_hold_drag` 与 `vm_slider_drag` 原来直接向 `/vm/hold_drag`、`/vm/slider/drag` 发出按下、移动、松开动作。现在它们在共享传输入口返回 `preview_and_confirm_required`，不发 HTTP；即使内部 `verified_click=True` 或模型参数带同名字段也不能放行。模型工具说明明确标为暂不支持：现有单点 ticket 不能授权完整拖拽。这是暂时关闭两个绕行入口，不是已实现通用手势支持；恢复拖拽须绑定动作种类、完整路径、按钮、时长及当前截图，并让模型先看到相应标记再确认，不能拿单点点击 ticket 替代。

离线集成进一步覆盖原生模型循环 → 实际分发 → 实际 HTTP 序列化（仅替换网络边界）：带中文、emoji、换行、CRLF、制表符及 shell 特殊字符的完整 `vm_type` 文本恰好产生一个 `/vm/type` POST，未调用按键/逐字符循环。这证明插件没有拆分或改写文本；VM 服务端是否完整粘贴仍需另行评审其实现，不能据此宣称真实桌面验收。

全工具离线审计同步将两个拖拽入口的精确拒绝回执归类为 `click_checkpoint_required`，不计为执行成功：当前预期为 99 个 acknowledged、3 个 capability_unavailable、6 个 click_checkpoint_required。处理器发现来自实际 AST 门禁分支，而不是伪造 HTTP 映射；错误名称、其他错误及非布尔 false 的回执仍会失败。此前审计产物属于旧基线，不能作为当前拖拽可用的证据。

### 能力信任边界与下一步设计

- `vm_exec` 向 `/vm/exec` 发送 Python/Shell；`vm_job_start` 经同一入口启动任意脚本。`vm_eval`、`vm_frame_eval` 执行任意浏览器 JS，并非只读观察接口。保留这些能力意味着模型可能通过脚本、CDP/DOM、显示服务或直接 HTTP 绕过插件点击检查点，不能宣称“所有点击都必须确认”。shell 命令 denylist 无法证明任意程序不操作 GUI，本次不添加这种假保证。
- `vm_type`、`vm_key` 保持可用；聚焦控件中的文本或 Enter 也可能触发应用动作，不等价于受到点击 gate 约束。其他浏览器自动化入口（例如网页登录）同样需检查服务端实现。
- 当前 `full/light` 工具 profile 只改变 schema 展示，不构成执行权限。现有原生 QQ 发送的目的地策略与成功回执也不约束任意 VM 代码；本次不改发送规则、终端能力或全局 profile。
- 要达成完整中介，需先纳入并核验真实 VM 服务端基线，然后由受信运行时持有独占 GUI/浏览器控制能力：模型只调用结构化预览/确认/文本 API；终端运行身份仍可正常执行程序，但不能访问显示套接字、输入设备、CDP、GUI HTTP 凭据或同权限辅助进程。仅去掉 `DISPLAY` 或隐藏 schema 不能达成隔离。图片观察回执和一次性动作票据须在该中介边界验证。
- 如必须保留同权限原始执行，应明确称为“受信执行”模式；可单独评审用户显式选择的 guarded desktop profile，但没有真正的操作系统/运行时能力隔离时，不能把 opt-in profile 也称为完整安全边界。本次没有新增或强制选择任何 profile，也没有部署或访问实际桌面。

## 实测与剩余限制

离线集成覆盖真实插件原生模型循环（用替代的截图/模型/鼠标操作以免操作线上屏幕）以及更换屏幕、假标点、复用 ticket、跳过视觉请求、同批次确认等失败路径。插件依据实际完成的含图模型请求标记 `observed`；但无法从服务端证明模型主观上识别正确目标，`viewed=true` 仍是模型的显式复核声明。此视觉检查点只覆盖插件经模型暴露的点击工具；原始 VM 服务端的 HTTP 路由与可执行脚本、浏览器脚本等独立能力仍可间接发起鼠标事件。尚未做真实屏幕可视化验收，不能声称已覆盖所有绕行路径或绝对免除截图与点击之间的物理竞态。进一步服务端统一收口需先把 VM API 纳入仓库、核对实际部署基线及完整能力回归，并走独立受控发布。

独立 QQ 的原生登陆、收发和功能等价验收仍未完成，不能作为此项插件改动的完成条件代用品。
